# verify-app · ตรวจแอปก่อนบอกว่าเสร็จ

ทำทุกขั้นตามลำดับ ห้ามข้าม ห้ามสรุปว่าผ่านจากความจำหรือจากการอ่านโค้ด ต้องมาจากผลที่รันในรอบนี้เท่านั้น

## 1. เปิด dev server
- รันแบบเบื้องหลัง (Bash `run_in_background: true`) จากรากของ repo:
  `python3 -m http.server 8000`
- รอจนพร้อม: `until curl -sf http://localhost:8000/ >/dev/null; do sleep 0.5; done` (ใส่ timeout 30 วินาที)
- ถ้าพอร์ต 8000 ถูกใช้อยู่ ให้ใช้พอร์ตอื่น แล้วเปลี่ยน `BASE_URL` ในขั้นถัดไปให้ตรงกัน

## 2. รัน test ที่เกี่ยวข้อง
1. ดูว่าแก้อะไรไป: `git diff --name-only origin/main` และ `git status -s`
2. เทียบไฟล์ที่แก้กับ "ไฟล์หลัก" ของแต่ละฟีเจอร์ใน `FEATURE_MAP.md` แล้วจดว่าฟีเจอร์ไหนเกี่ยวข้อง
3. รัน flow หลักผ่าน dev server (ใช้เวลาราว 20 วินาที):
   `BASE_URL=http://localhost:8000/ node tests/flows.js`
   ถ้าจะไปขั้น 5 ทันทีโดยไม่แก้อะไรระหว่างนั้น ข้ามขั้นนี้ได้ แล้วใช้ภาพและ log ของ flows จาก `npm run check` ในขั้น 5 แทน (อยู่ที่ `test-results/flows/` เหมือนกัน) จะได้ไม่รัน flows ซ้ำ · ขั้น 5 ต้องรัน `npm run check` เต็มชุดเสมอ เพราะ hook Stop ยอมรับเฉพาะการรันครบทุกขั้น
4. รันข้อ e2e ของฟีเจอร์ที่เกี่ยวข้อง: บรรทัด **test** ของ FEATURE_MAP เขียนเป็น `e2e.js "<คำ>"` ให้ใช้คำนั้นตรงๆ เช่น
   `node tests/e2e.js "ไวยากรณ์:"` (ชุดนี้เปิด server ของตัวเอง · ถ้าขึ้น `ผ่านทั้งหมด 0 ข้อ` แปลว่าคำไม่ตรงชื่อข้อ ให้แก้ FEATURE_MAP)
5. ก่อนบอกว่าเสร็จ รันทั้งชุด: `npm run check` (type → lint → determinism → featuremap → unit → hooks → e2e → flows ราว 3–4 นาที) และ `node tests/check-version.js origin/main`
6. ถ้าแก้แมวพิกเซลหรือฉาก ให้รัน `node tests/pet-grid.js test-results/pet-grid` เพิ่มด้วย

## 3. เปิดดูภาพหน้าจอ
- หลักฐานอยู่ใน `test-results/flows/` และ `test-results/e2e/` (ดูรายชื่อภาพของแต่ละข้อได้ใน `summary.md`)
- ใช้ Read เปิดภาพจริงอย่างน้อย 1 ภาพต่อ flow ที่เกี่ยวข้อง และทุกภาพของข้อที่ไม่ผ่าน (`<ข้อ>-end-p1.png` คือหน้าจอตอนจบข้อ)
- ดูว่าภาพตรงกับที่ flow ควรเป็น: ข้อความไทยไม่ล้น ไม่มีหน้าว่าง ไม่มีส่วนที่ซ้อนทับกัน และปุ่มอยู่ในจอ
- ถ้าภาพผิดแต่ test ผ่าน ให้ถือว่าไม่ผ่าน และบอกว่า test ยังจับจุดนั้นไม่ได้
- ภาพจาง (ถ่ายระหว่างแอนิเมชัน) ว่างทั้งภาพ หรือเห็นแค่หน้าโหลด = **ยังไม่มีหลักฐาน** ห้ามนับว่าผ่าน ให้ถ่ายใหม่หลังหน้าจอนิ่ง (`rec.shot` ใน `tests/artifacts.js` ปิดแอนิเมชันให้แล้ว ถ้ายังจางแปลว่าถ่ายเร็วไป) หรือรายงานว่าข้อนั้นยังไม่มีภาพยืนยัน

## 4. อ่าน console error
console error ใน log ต่อท้ายด้วย ` @ <URL>` ที่เกิด แยกเป็น 3 กลุ่ม:
1. **JavaScript error ของหน้า ต้องเป็น 0 เสมอ** (มีแม้บรรทัดเดียว = ไม่ผ่าน):
   `grep -n "\[p[0-9]* pageerror\]" test-results/*/*.console.log`
2. **ที่ตั้งใจ ไม่ใช่ปัญหา**: `Failed to load resource` ที่ URL เป็น `https://sb.test/` คือ Supabase จำลองใน `tests/e2e.js` ตอบ 404/403/409 ตามที่ข้อซิงก์/ซื้อ/แพ็กตั้งใจทดสอบ
3. **error อื่นทั้งหมด ต้องอธิบายได้ทุกบรรทัด** ไม่งั้นถือว่าไม่ผ่าน:
   `grep -n "\[p[0-9]* error\]" test-results/*/*.console.log | grep -v " @ https://sb.test/"`
- ข้อที่ไม่ผ่าน: อ่าน `test-results/<ชุด>/<ข้อ>.console.log` ทั้งไฟล์ (บรรทัดบนสุดคือข้อผิดพลาดของ test)
- `warning` ที่เป็น "Service Worker registration blocked by Playwright" เกิดจากการตั้งค่าของ test เอง ไม่ใช่ปัญหาของแอป

## 5. สรุป
ตอบเจ้าของด้วยตารางนี้ หนึ่งแถวต่อ flow ที่รัน:

| flow | ผ่าน/ไม่ผ่าน | หลักฐาน |
|---|---|---|
| ชื่อ flow ตาม FEATURE_MAP | ✅ ผ่าน / ❌ ไม่ผ่าน (สาเหตุสั้นๆ) / ⚠️ ไม่ผ่าน · ปัญหาเดิม | ชื่อไฟล์ภาพ · จำนวน console error · บรรทัดผล test |

ใช้ **⚠️ ไม่ผ่าน · ปัญหาเดิม** ได้เฉพาะเมื่อมีหลักฐานว่าไม่ผ่านแบบเดียวกันก่อนงานนี้ และงานนี้ไม่ได้ทำให้แย่ลง: ระบุสิ่งที่เทียบ (เช่น lint ก่อนเริ่มงาน 134 error ตาม `docs/HANDOFF.md` → ตอนนี้ 132 · ผล CI ของ commit ก่อนหน้า · แผนแก้ใน `docs/LINT_PLAN.md`) · ถ้าเทียบไม่ได้ ให้ใช้ ❌ ไม่ผ่าน

แล้วตามด้วย:
- บรรทัดสรุปผลจริงของแต่ละชุด เช่น `ผ่านทั้งหมด 58 ข้อ` หรือ `ไม่ผ่าน 1/7`
- อะไรที่ยังไม่ได้ตรวจ (เช่น iPad Safari จริง, Apple Pencil จริง)
- ข้อที่ไม่ผ่าน: บอกตรงๆ ว่าไม่ผ่าน ห้ามบอกว่าเสร็จ ห้ามแก้ test ให้ผ่านโดยไม่แก้ต้นเหตุ

## 6. ปิด dev server
หยุด server ที่เปิดในขั้นที่ 1: `pkill -f "http.server 8000"` (เปลี่ยนเลขพอร์ตถ้าใช้พอร์ตอื่น)
